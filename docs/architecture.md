# Personal Word architecture

A single-writer, Mac-first desktop application. Tauri 2 hosts React/TypeScript and Tiptap 3 (ProseMirror). Rust owns SQLite and file access. No network service, accounts, or AI. The one outbound request is the opt-in citation lookup: when the writer clicks Look up, the typed DOI, ISBN, or web address is sent to Crossref, Open Library, or that website (natively through the `lookup_fetch` Rust command: http/https only, 12 s timeout, 3 MB cap). The browser development preview uses explicitly labeled browser storage, still one whole-project blob per save; it is not desktop persistence.

## Boundaries

- React owns navigation and an in-memory project. The main Tiptap instance follows the active section or fragment; section changes remount it to isolate undo histories. The fragments panel can also mount inline editors for other fragments.
- A serialized save coordinator owns the recovery journal, debounce, flush, and errors. Every edit journals immediately. Navigation does not cancel pending writes. The frontend handles the actual native close request, waits for writes and portable copies, and leaves the app open when either fails.
- Rust validates project identity, revisions, document shape, and references, then commits changes in a SQLite transaction. SQL is parameterized. Schema versioning uses user_version (currently 2; version 1 databases are migrated in one transaction on open); newer schemas are rejected.

## Model and storage

Project: ID, title, created/updated timestamps, revision, ordered section IDs, entries. Entry: ID, kind (section/fragment), title, ProseMirror JSON, plain text, updated timestamp, optional source section/selection/context. A project has one manuscript in this milestone. Research sources, notes, footnotes, comments, and entry tags are additive project/entry metadata. Content-addressed binary assets (PNG, JPEG) are stored in the SQLite `assets` table and mirrored to disk under `attachments/<asset_id>.<ext>`. Source PDFs use the same table and the same staging path (`stagePdf`/`readPdf` in `src/storage.ts`); a pane draws one from a blob URL revoked on unmount (`src/research/PdfPane.tsx`), and deleting a reference leaves the bytes in place.

Application data lives in the OS application-data directory under com.folio.writing. Each UUID project directory contains `project.sqlite3`, `project.json`, `manuscript.txt`, `fragments.txt`, and `attachments/`.

SQLite is the source of truth. The `project` table holds one small header row (title, timestamps, revision, section order, and the ordered list of entry IDs) and no prose. The `entries` table holds one row per section or fragment (ID, kind, JSON). The `assets` table stores binary attachments (`id TEXT PRIMARY KEY`, `mime TEXT`, `byte_length INTEGER`, `width INTEGER`, `height INTEGER`, `data BLOB`, `created_at INTEGER`). Images are staged in isolation via `stage_assets` before the edit that references them commits. A native kill after staging and before that edit left the visible project and history unchanged, and the retry committed with the image attached (T018, `post-asset-stage`). In the shared editor schema, rich nodes include `image` (with `assetId`, `alt`, `title`), `table`, `tableRow`, `tableCell`, and `tableHeader`, subject to strict rectangular non-nested constraints. Research source merges validate their updates, write a safety snapshot first, then commit once; a native kill after the safety snapshot showed no merge and a byte-equal safety copy (T018). Reading a project rebuilds it from the header plus the entry rows inside one read transaction. A save upserts only the entries that changed, deletes entries the header no longer lists, checks that every listed entry exists and that the order names exactly the sections, verifies that all referenced asset IDs are present in the database, then replaces the header — all in one immediate transaction. Named snapshots are separate rows holding complete project JSON, and also standalone JSON files.

project.json, manuscript.txt, fragments.txt, and attachment files are portable copies, not part of the save transaction. A background thread writes attachments before `project.json` at most every 3 seconds for projects saved since the last pass, and immediately on ⌘S, Retry, returning to the library, and quit. Each file is atomically replaced (same-directory temporary file, fsync, rename, directory fsync). The pass reads SQLite outside the store lock, so saves never wait on it. A failed pass keeps the project pending, shows "Database saved, but portable copy failed … Retry to repair it" in the error banner, and is retried by the next pass or by Retry; quit is blocked until it succeeds. On startup or when opening a project, `Store::load` inspects the disk mirror revision against SQLite: if `project.json` lags behind the committed SQLite revision, the project is automatically queued into the dirty set for background mirror repair. This is covered by the Rust test `stale_portable_copy_is_repaired_after_a_restart` and by the native `post-commit-pre-mirror` scenario (D1, T018); it covers an app restart, not a power loss.

## Save, history, and recovery

Every edit bumps the project revision and writes the recovery journal synchronously to WebView localStorage: the changed entry under its own key plus a small header (title, order, revision, entry IDs, and which entries are journaled). Unchanged entries are neither copied nor serialized, so a keystroke costs the size of the section being edited, not the project. The journal is synchronous to memory only: WebKit writes localStorage to disk on its own schedule with no fsync, so it protects against reloads and in-app failures, not against a hard kill or power loss.

Autosave uses a responsive 250 ms trailing debounce and a 2,000 ms maximum scheduling wait from the first pending edit. The latter bounds when a healthy queue attempts persistence; slow I/O, errors, suspension, and blocked event loops can exceed it. The coordinator sends Rust the header plus the entries whose objects differ from the last state confirmed on disk, along with that state's revision. Rust refuses a delta built on a revision the disk never reached. Writes are serialized and reject stale revisions; a same-revision retry is a no-op when it matches what is stored and a conflict otherwise. After any failed save the coordinator forgets what is on disk and the retry sends every entry. Journal keys clear only after the newest journaled revision is persisted. On opening, a newer journal is rebuilt on top of the saved project (or alone, for a project never saved) and saved; an incomplete, malformed, or same-revision-but-different journal is kept and reported instead of guessed at. Journals from the previous whole-project format are still recovered.

SQLite uses WAL and synchronous=FULL. On macOS every project database connection opened by the store also sets `fullfsync=ON` and `checkpoint_fullfsync=ON` (the `previous-session.sqlite3` backup copy is written with SQLite's backup API and ordinary sync), requesting Apple's stronger `F_FULLFSYNC` operation for commits and WAL checkpoints. In three release-mode runs at load about 2 on this Intel Mac, a 100,000-word active-entry delta save measured p95 116.57 / 130.43 / 124.37 ms and median about 108 ms against the 150 ms budget (T018, `wp11-matrix.md` section 5). That is one machine's measurement. Apple silicon is unmeasured, and earlier runs at host load 49 to 107 measured p95 347 to 499 ms (D1), so a busy Mac can exceed the budget; `SaveQueue` keeps typing in memory and in the recovery journal meanwhile. This improves the requested flush behavior; it cannot guarantee survival of a power cut, storage-controller failure, or OS kernel panic. Edits not yet committed exist only in memory and the WebView journal. The maximum scheduling timer prevents healthy continuous typing from indefinitely postponing a save attempt, but it does not guarantee a fixed loss window under slow I/O or failure. Physical power loss and hardware failure are not claimed and have not been tested; external backups remain necessary.

The native editor's `Saving…`, `Unsaved edits`, and `Save failed` labels describe the save coordinator. `Saved` means the latest queued write completed successfully through SQLite; portable JSON/text copies are a separate path and may still lag or show a retryable error. Neither state means an external backup exists. A successful save acknowledgement is distinct from the local recovery journal, portable mirrors, and an external backup.

Automatic recovery history is separate from named milestones. Before each new revision is written, the current state is archived: its header and, per entry, a pointer to a stored entry version. Each entry version is stored once and shared by every history row that contains it, so typing in one section adds one section-sized blob per save, not a project-sized copy. Retention is by time, in clock-aligned windows: every save from the last 10 minutes, the newest save per 5 minutes for the last day, the newest per hour beyond that, and never more than 2,000 rows (oldest dropped first). Entry versions no longer referenced are deleted in the same transaction. Named snapshots store complete project content and ordering. Restoring creates a new revision; first the UI creates a safety snapshot of current writing. Fragment extraction changes section and fragment in the same save transaction; provenance remains on the fragment. Restoring copies prose into a chosen section, retaining the original fragment.

## Backups and portability

On opening a database, use SQLite's online backup API to make a previous-session backup. Never copy a live SQLite main file alone. Portable mirrors provide an independent recovery route; import validates them before creating a new project identity. Copy the whole project folder when the app is closed for an external backup. Local backups do not protect against disk loss; external backup is still necessary. No silent corruption reset. Errors keep the journal and show an actionable retry.

## UI

Quiet warm-neutral chrome, restrained accent, serif writing surface, compact formatting toolbar, sidebar for ordered manuscript and fragments. Native-feeling keyboard controls. Drag reordering has accessible move-up/down alternatives. Snapshot inspection is read-only; restoration is explicit. Focus mode hides the sidebar. Continuous read view is read-only in this milestone.

## Source organization and boundaries

`src/model.ts` owns project/entry invariants; `src/save-queue.ts` owns journaling and serialized save scheduling; `src/storage.ts` selects native versus browser adapters; `src/editor/` owns the shared Tiptap schema and editor layout; `src/research/` owns citation/research behavior; `src/organization/` owns fragments, comments, and comparison; `src/import/` owns manuscript decoding; `src/export/` owns the shared document representation and DOCX/PDF renderers. `src/App.tsx` remains the lifecycle/orchestration join point, and `src/Writer.tsx` owns the mounted editor and toolbar/layout composition. Domain and persistence remain independent of React views.

The native app takes an advisory Unix `flock` on a file at the library data root. A concurrent desktop instance using the same root fails at startup with a clear message; the operating system releases the lock when the process exits. This does not create cross-device or network-filesystem coordination guarantees.

Plain UTF-8 `.txt` and Markdown (`.md`, `.markdown`) import creates a new project (5 MB maximum) after a preview step that shows the format, an excerpt, and warnings; the source file is left unchanged. Markdown is parsed into the shared editor schema without a DOM or HTML execution path: headings, emphasis, strong, strike, links (http, https, mailto), nested lists, block quotes, inline and fenced code, and line breaks are represented; images, tables, relative links, and raw HTML are retained as visible literal text with a warning, and no remote resource is fetched. JSON recovery remains a separate full-project path.

Rich import (beta board, CLAIMED): `src/import/docxImport.ts` routes `.docx`, `.html` and `.zip` files (20 MiB compressed at most) beside the text path. DOCX and Markdown-bundle zips are checked from the central directory (entry count, per-entry and total size, compression ratio, encrypted entries, path traversal) before JSZip inflates anything; HTML is parsed by an inert `DOMParser`; an external image relationship is omitted with a warning and nothing is fetched. Images become staged `PendingAsset`s and are saved through `createProjectWithAssets` only after the preview's Import is chosen; Cancel (and the cancellable busy dialog during a parse, `src/App.tsx` `importWriting`) creates no project. The preview counts picture nodes, and embedded media that no drawing references is not staged. Limits that remain: a zip whose headers understate an entry is rejected by JSZip only after that entry inflates (owner question Q003); the XML check blocks only external DOCTYPEs; no WebKit or native run of these paths. BibTeX (`src/research/bibtexImport.ts`, 5 MB) and the optional Zotero refresh (`src/research/zotero.ts`, native `zotero_read` in `src-tauri/src/zotero.rs`, 127.0.0.1:23119 `/api/` only, GET only, no redirects, 5 MiB cap) feed the same reviewed source-merge dialog; the desktop app uses the native command and the browser preview uses `fetch`, a difference from the approved design. Plain `.txt` and `.md` import above is unchanged: it still keeps images and tables as literal text.

DOCX and PDF currently preserve text, bold, italic, underline, strike, links, heading structure, lists (including nesting and ordered start values), page breaks, paragraph alignment/indent/spacing, footnotes, and optional bibliography in their shared representation. DOCX uses native Word numbering, footnote, and strike markup. PDF embeds bundled OFL Noto Serif, Noto Sans, and Noto Sans Mono subsets for the selected document typeface, covering Latin, Latin Extended, Greek, and Cyrillic; it does not use document fonts, does not shape complex scripts, rejects scripts outside those ranges, rejects footnotes that cannot fit on a single page, and may split long tokens at Unicode code-point boundaries. Both exporters use independent pagination engines.

Beta board additions to the exporters (CLAIMED): images and rectangular tables flow through DOCX (inline drawings, `w:tblHeader` on the header row), PDF (PNG/JPEG drawn inline; the header row is not repeated on continuation pages), Markdown, plain text and the Markdown bundle (`manuscript.md`, `assets/<sha256>.<ext>`, `manifest.json`; hashes are verified on import). The Markdown bundle round trip and the v2 project archive are covered by unit and Chromium tests. DOCX and PDF omit the project title and section titles that Markdown, plain text and the bundle print. A footnote with several paragraphs is written as separate paragraphs in DOCX and PDF (task T043, repaired and independently reviewed; before it, PDF refused such a note with a misleading script error and DOCX wrote one run with literal line feeds).

Native print: a WKWebView `NSPrintOperation` probe (`src-tauri/src/printing.rs`, `src/print/`, task T013) reached a documented STOP: Arabic with the lam-alef ligature was not searchable in the printed PDF with 26 of 28 installed fonts. Its `render_pdf` command is registered only in the `native-smoke` diagnostic build; normal builds compile the module as dead code. The legacy pdf-lib exporter is the only PDF path. An exact PDF preview (WP9) and flowing per-page footnotes (WP10) were cancelled pending owner question Q004. Editor pages, DOCX and PDF still use three layout engines, and no page parity is promised.

## Risks and deliberate limits

Opening a project still loads and validates every entry (about 45 ms of Rust for 100,000 words, mostly JSON parsing), and each portable-copy pass rewrites the whole project.json (about 200 ms at that size, off the save path). See validation.md for measured per-keystroke and per-save costs. Research and DOCX/PDF export are implemented with the limitations above. Cross-section editing, merged or nested table cells, images other than PNG/JPEG, and alternate drafts remain outside scope. OS spellcheck availability depends on WebView. Journal storage can fill: surface failure, keep memory, and attempt disk persistence. Native testing of real shutdown and power loss (only owned-process kills at named checkpoints are tested), signing/notarization, and broader accessibility QA remain release gates. Browser tests are not evidence of native WebView behavior.
