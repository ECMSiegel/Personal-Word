# T237 -- Ruler and continuous-view top gap

## Decisions and implementation

- The **Ruler** toggle (now inside Page setup, see Rework) is off by default and stored as the additive global preference
  `folio.workspace.ruler`. In split view, both pane rulers follow that preference, while each ruler
  is sized and zoomed with its own pane.
- The ruler uses real tick elements (not a gradient) and two keyboard-focusable margin sliders.
  Both markers are linked: moving either updates the existing single document margin. Dragging
  previews the marker and commits one layout change on release; Arrow keys adjust by 1/16 inch,
  Shift+Arrow by 1/4 inch, and Home/End go to the limits.
- The screen margin cap is 2 inches (192 CSS px), matching the existing DOCX/PDF and native-print
  limit. This removes the old 1.5-inch screen/export mismatch; it does not change existing exports.
  The margin dropdown now includes 1 1/4, 1 1/2, 1 3/4 and 2 inch presets (unrequested; the owner's call to keep or drop -- they change nothing silently).
- Continuous-view top spacing is additive `pageLayout.topGap`, defaults to 32 px for old projects,
  and validates from 0 to 200 px. It changes only the top padding in continuous view. The page
  separation remains fixed at 32 px; page-view top padding remains the real document margin. The
  gap handle is present only while the ruler is on and the view is continuous. It supports vertical
  dragging and ArrowUp/Down (Shift for 16 px; Home/End for limits).
- `App.tsx` updates `documentSettings.marginInches` only when the actual document margin changes.
  Therefore a top-gap-only edit cannot alter export margins. The top gap is not read by DOCX/PDF
  exporters; a regression test reads the exported Word section margins and checks the screen-only
  gap is absent.
- Cmd-Z does **not** undo a ruler drag. A drag is committed like the existing margin dropdown, not
  placed on the editor's text undo stack.
- `src/editor/editor.css` also has a separate, pre-existing W7 B change near the top-bar dropdown
  rule; I left that region untouched. No command-palette entry was added because the authorized
  shared `App.tsx` scope was limited to the margin-sync callback and the direct request is met by
  the toolbar toggle.

### D7 -- owner-overridable choice (coordinator decision, with one deviation)
The coordinator asked for the Ruler toggle inside the existing More menu. At the owner's 1440 window there is no More menu (design-system: the whole toolbar fits), and any More button costs at least the width of the Ruler button that already pushed Focus mode and Prose check into More, so a More-only toggle would be unreachable at 1440 or would move those buttons again. The toggle is therefore a text button (`aria-pressed`) in the Page setup panel, sharing the row of "Insert page break" (so the panel keeps its recorded 232 x 136 size). Page setup is itself a More row on narrow windows, so it is reachable from More there. Toolbar: no new button, Focus mode and Prose check stay put, no baseline re-record. The owner may prefer a View-menu-style home or a toolbar icon (at the cost of More appearing at 1440 and a baseline re-record). `docs/design-system.md` has no ruler text yet; whoever owns the docs should add: ruler lives in Page setup; page variables on the viewport; clip not hidden on `.is-paged`.

Known, pre-existing: in continuous view `.writing-surface` has `padding: 0 8px` (styles.css), so the first glyph sits 8 px inside the margin the ruler marks; page view has none. Not changed (shared file, visible text shift).
