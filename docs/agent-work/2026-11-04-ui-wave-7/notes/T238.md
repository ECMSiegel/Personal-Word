## Root causes (one per cluster)

### 1. footnotes:48, footnotes:134 -- focus war between two auto-focus effects

CI error: `expect(locator).toBeFocused() failed ... element(s) not found` for
`getByLabel("Footnote 1 text")` -- the editor's auto-opened footnote field was
gone (closed by blur) when the test looked for it.

Mechanism (code-verified):

- `ResearchPanel.insertTextOnly` (src/research/ResearchPanel.tsx:163-166)
  calls `onInsertFootnote(id)` then `setPendingFocus(id)`.
- `onInsertFootnote` -> App.insertFootnote (src/App.tsx:1569-1577) ->
  `editor.chain().focus().insertContent(footnoteReference).run()`.
- Writer's new-note effect (src/Writer.tsx ~835-852) watches
  `[referencedKey, notesKey]` and sets `editingNote`, which mounts
  `FootnoteTextarea` with `autoFocus` and `onBlur={onDone}`
  (src/editor/FootnoteArea.tsx:152-154): the editor field CLOSES when it loses
  focus.
- ResearchPanel's `pendingFocus` effect (lines 125-134) then focuses the
  panel's own `[data-research-id]` textarea ("Footnote text") in the same or a
  later commit. When that lands after the editor field mounted, it steals
  focus -> `onBlur` -> the editor field closes -> the test's target is gone.

Whether the steal happens depends on commit interleaving, which is why this
passes locally and failed on the slow runner.

Fix (my file): remove `setPendingFocus(id)` from `insertTextOnly`. The panel
field for a brand-new text-only footnote does not need focus; the editor's
auto-opened field is the primary surface and what the specs assert. Keep
`setPendingFocus` in `citeHere` (cited notes do not auto-open an empty editor
field, no collision) and in the click-a-footnote path (floating.spec asserts
it).

### 2. markdown-roundtrip:190/281/379/406 + assets:281 -- toolbar click defers editor focus by one frame

CI errors: first `th` received `ol A` (leading "C" swallowed), and in the worst
case the header row is gone with the "Table controls" dialog open.

Mechanism (code-verified):

- Tiptap's `focus()` command NEVER focuses synchronously on Chromium: it calls
  `delayedFocus()`, which defers `view.focus()` to `requestAnimationFrame`
  (node_modules/@tiptap/core/dist/index.js, `const focus = ...`).
- Our toolbar buttons do not preventDefault on mousedown
  (`popoverItem(inMore)` in src/Writer.tsx:1119-1120 is only a data attribute),
  so clicking "Insert table" blurs the editor; `chain().focus()` inside the
  click handler refocuses only on the NEXT frame.
- The test (and a real user) starts typing immediately. On the slow runner the
  first keystroke lands while focus is still on the toolbar: the character is
  swallowed ("ol A"), and Space activates the still-focused toolbar button --
  in the CI snapshot the "Table controls" button got the Space, its dialog
  opened, and later Tabs/Spaces reached the dialog (header row toggled off).

This is a real UX bug (lost keystrokes after clicking a toolbar button), not
just test timing.

Fix (Writer.tsx -- T237 owner agent-0461, coordinated via message #1201): in
the Insert-table onClick, after `.run()`, call `editor.view.focus()` so DOM
focus is synchronous. (Alternative: preventDefault on toolbar mousedown; more
invasive, touches every button.)

### 3. split-view:155 -- blur ate the in-flight selection sync; apply hit storedMarks

CI error: `span[style*="Georgia"]` not found in either pane, while the toolbar
label shows "Georgia" and Bold had applied (`<strong>Left sample</strong>`).

Mechanism (proven deterministically, see evidence run 6):

- The test does `left.click()` (caret placed), `Cmd+A` (select all), then
  clicks the Font family trigger and picks Georgia.
- ProseMirror only syncs the DOM selection into state while the editor is
  focused (`hasFocusAndSelection` guard in prosemirror-view's
  `DOMObserver.onSelectionChange`/`flush`, node_modules/prosemirror-view/dist/
  index.js:4826). The browser delivers `selectionchange` as a TASK after the
  keydown.
- The Font trigger does not preventDefault mousedown, so the trigger press
  blurs the editor. On the loaded runner the dismissal of the still-open More
  menu (React commit + `fitToolbar`'s synchronous offsetWidth measurements)
  sat between the Cmd+A and the trigger mousedown (trace: Cmd+A at
  uifc@44958, font click action starts 10 ms later), so the queued
  `selectionchange` landed after the blur -- PM never saw the select-all,
  state kept the caret from `left.click()`.
- `chain().focus().setMark("textFormat", ...)` then applied to the caret:
  storedMarks only. Label flips to Georgia, no span anywhere. (The screencast
  highlight that disappears at 1317546.7 is the blur repaint, not the
  selection being destroyed.)

Trace/geometry findings (CI trace /tmp/w7-ci/sv-trace, frames re-extracted to
/tmp/w7-ci/sv2 with timestamps): the left editor (x368-527) was NOT covered by
the More menu (x594-810), so `left.click` landed cleanly; the Georgia option
(x542-690, click point 616,252.5) DID overlap the still-mounted closing menu,
which is why that click took 211 ms. The More menu stays mounted ~150-250 ms
after dismissal (Popover `usePresence` exit animation, role/aria dropped at
once while closing -- src/components/Popover.tsx:325-330), which is why the
test's `toHaveCount(0)` passes during the exit animation. The overlap alone
does NOT cause the failure: forcing it locally (CDP
`Animation.setPlaybackRate` 0.1 + 6x throttle, 4 repeats) still passed.

Fix (my files): new `SelectionKeep` extension (src/editor/selectionKeep.ts,
registered in src/editor/extensions.ts). On editor blur it reads the DOM
selection; if it is non-collapsed, inside this editor, and differs from
state.selection, it dispatches `setSelection` so state matches what the user
saw on screen. Collapsed selections are ignored (a caret carries no intent);
WebKit clears the selection on blur, so there the handler is a no-op. This
makes any toolbar/dropdown apply robust against the blur-vs-selectionchange
race, not just this test's path.

### 4. floating:790 -- reduce-motion card still hidden for one frame

CI error: card `opacity` expected "1", received "0" (Reduce Motion test).

Mechanism (code-verified): `CitationCard` starts `shown = !animateIn`
(src/research/CitationCard.tsx:44); with a mouse open (`animateIn=true`) the
card first renders with `opacity: 0` and only flips `data-shown` one
requestAnimationFrame later (lines 60-64) -- even under Reduce Motion, where
the promised behavior is "opens without a transition" (instant). The test
reads opacity right after `toBeVisible()`, which can land inside that first
frame on a slow runner.

Fix (my file): initialize `shown` to `!animateIn || prefersReducedMotion()`
(src/motion.ts already exports the helper) so the reduce-motion card is opaque
in its very first committed frame. The animated path is unchanged.

### 5. motion:36 -- fixed 300 ms sample window vs a 220 ms transition that starts late

CI error: final `animatedProperties(page)` received `["clip-path"]`.

Mechanism (code-verified): `.library-search-field` transitions clip-path over
`--duration-morph` (220 ms, src/components/library.css:21). `sampleDuring`
closes its window 300 ms after the click resolves; on a loaded runner the
style flush (and thus the transition start) can happen >80 ms after the click,
so the transition outlives the window. The samples themselves only ever
contained allowed properties.

Fix (my file, test-side, not a weakening): before the final
"nothing is running" assertion, wait for `document.getAnimations()` to drain
(the same pattern `revealSidebar`/`openProjects` already use). The assertion
still catches leaked/never-ending animations (the wait times out), and the
allowed-properties check on the samples is unchanged.

### 6. writing-aids:21 -- focus-dim class never applied (CI-only flake)

CI error: `p.nth(1)` class "" (no focus-dim) for 5 s after clicking Focus mode.

Code-level race (not reproduced locally): the FocusMode plugin
(src/editor/writingAids.ts:89-107) computes decorations only when
`this.options.enabled()` is true, and the refresh transaction is dispatched
from an effect on `[editor, focusMode, proseCheck]` (src/Writer.tsx:815-822).
If the refresh lands in the window where the enabled option still reads
false, no later transaction recomputes the decorations and the dim never
appears until the next selection/keystroke. Reproduction attempts: throttle
6x plain, and `--repeat-each=20` under throttle on the fixed build -- 300/300
passed (node_modules/.cache/personal-word-beta/ui7-ci/writing-aids-x20.log).
Local hardware cannot stretch the window enough; the CI runner's ~1-in-8
rate suggests a slow-commit interleaving. No test change made (weakening the
5 s wait would hide real regressions); the race window could be closed in
Writer.tsx by dispatching the refresh whenever `enabled()` flips, which
belongs to the T237 lane's Writer.tsx work -- flagged in the done note for
the coordinator.
