## Findings (ranked)

### 1. HIGH -- floating + unpinned: hover-reveal collapses before the pointer reaches the sidebar (C3, implementation defect) -- REPAIR BEFORE SHIP
- Where: `src/components/floating.css:12-24` (shell `pointer-events: none`, children `auto`), `:30` (the floating `.sidebar` starts at `left: var(--space-4)` = 16 px); `src/styles.css:1588-1596` (`.sidebar-edge` is 8 px wide at `left: 0`); `src/components/ProjectSidebar.tsx` `onMouseLeave` of the shell (`if (!aside.current?.contains(document.activeElement)) setRevealed(false)`).
- Evidence (probe, current build, 1600x900, floating on, unpinned): moving to x=3 reveals the sidebar; then moving the pointer one pixel at a time from x=4 to x=24 (30 ms per step) ends with `class="sidebar-shell is-overlay is-floating"`, `revealed=false`; `document.elementFromPoint(12, 450)` is `editor-viewport is-continuous <DIV>`, i.e. between the 8 px edge strip and the 16 px sidebar inset the pointer is over the workspace, so the shell's mouseleave fires and hides the sidebar. The wave's specs and V's "floating-revealed" shots pass only because they jump the gap in one `mouse.move(..., { steps: 4 })`.
- Why it matters: REQUEST.md B says floating keeps "the same pinned/unpinned/hover-reveal behaviour"; a real pointer moves continuously and never gets in.
- Repair: `floating.css`: `.sidebar-shell.is-floating > .sidebar-edge { width: var(--space-4); }` (strip meets the sidebar). Fail-first: a `tests/floating.spec.ts` case that reveals at x=3 then walks x=4..24 in 1 px steps and asserts `is-revealed` still set; it fails on the current tree.

### 2. MEDIUM -- floating + unpinned shell paints at z-index 60, not the 4 the C3 contract and its approval state (C3, implementation defect) -- REPAIR BEFORE SHIP
- Where: `src/components/floating.css:12-21` (`.sidebar-shell.is-floating { z-index: 4 }`, specificity 0,2,0) vs `src/styles.css:1558-1561` (`.sidebar-shell.is-overlay { z-index: 60 }`, also 0,2,0). `src/main.tsx` imports `./App` (which pulls `floating.css` through ProjectSidebar) before `./styles.css`, so styles.css wins the tie.
- Evidence (probe): pinned floating shell computed `z-index: 4`; unpinned floating shell computed `z-index: 60` with class `sidebar-shell is-overlay is-floating`. T209's done note and agent-2de6's approval both say "z-index 4 (<Popover 40)".
- Why it matters (consequence by reading, not probed): the floating column (x 28-274 at width 270) sits directly under the format bar's left dropdowns (zoom, paragraph style, font). When the sidebar is revealed and one of those menus (z 40) opens, the bare sidebar text should paint through the menu. Pinned and unpinned states disagree either way.
- Repair: `floating.css`: `.sidebar-shell.is-floating, .sidebar-shell.is-floating.is-overlay { z-index: 4; }`. Fail-first: assert computed `z-index` of the unpinned floating shell is `"4"`; fails now. Note (by reading, Low): the right-click ContextMenu's `z-index: 70` (`context-menu.css:11`) is local to the shell's stacking context either way, so a menu that extends past the sidebar's right edge can sit under the format bar/popovers (40) or the citation card (39); geometry makes this rare. Wave 6: portal the menu to `document.body` with `position: fixed`.

### 3. MEDIUM -- B2's inline `maxWidth` lifts the Dropdown's 320 px cap inside every scroll container (B2, implementation defect) -- REPAIR BEFORE SHIP
- Where: `src/components/Popover.tsx:191-194` (`popup.style.maxWidth = \`${natural.maxWidth}px\``) vs `src/components/dropdown.css:51` (`.dropdown-menu { max-width: min(320px, calc(100vw - 16px)) }`, unchanged at HEAD). An inline style beats the stylesheet.
- Evidence (probe, 1440 px window, 390 px aside, "Full citation again" open): `inlineMaxWidth: "374px"`, `computedMaxWidth: "374px"`, `data-bounded` set, rendered width 357 px, i.e. wider than any dropdown could be before the wave. The same applies to the Projects screen (`.library` is `overflow: auto`): its Sort menu may grow to roughly the window width minus 16.
- Why it matters: B2 was meant only to keep menus inside the aside (16.png); it silently changes the width of every menu inside a scrolling ancestor. design-system.md:63 already records the "wrap instead of size to content" deviation, not a widening.
- Repair: after `popup.removeAttribute("data-bounded")` read `const cssMax = parseFloat(getComputedStyle(popup).maxWidth)` and write `Math.min(natural.maxWidth, Number.isFinite(cssMax) ? cssMax : Infinity)`. Fail-first: add a `tests/popover-bounds.spec.ts` case at the 390 px aside asserting the menu width <= 320; fails now (357).
- Related, Low (by reading, `Popover.tsx:51-59`, `Popover.test.ts` "clamps maxWidth ... even when neither side fits"): with start alignment and a trigger that sits mid-panel, the clamped menu's right edge is `trigger.left + box.width - 16`, which still passes the boundary; the unit test accepts this. Wave 6: shift the popup left by the overshoot when `maxWidth` is set.
