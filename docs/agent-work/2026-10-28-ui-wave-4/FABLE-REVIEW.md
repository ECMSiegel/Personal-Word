## Findings

### 1. BLOCKER -- the shared hover rule reaches links inside the user's document (faux-bolds manuscript text on hover)
- Where: `src/styles.css:417-456` (the "Text-control emphasis" selector includes `a[href]` with no exclusion for editor or Read-view content). The schema does allow links: `src/editor/extensions.ts:15` (`StarterKit.configure({ link: ... })`), `src-tauri/src/store.rs:1134` (`"link"` in the mark allowlist), `src/styles.css:1016` (`.writing-surface a`).
- Scenario (reproduced in the browser pane on the current build): put a linked phrase in a section, hover it in the editor. Computed style on the `<a>`: at rest `transition: transform 0.12s` (already from this rule); on hover `-webkit-text-stroke-width: 0.64px`, `--emph-s: 1.04`, `transform: matrix(1.04 ...)`. The document's own text is drawn bolder under the pointer. The Read view renders document links as `<a href>` too (`src/components/ReadDocument.tsx:73`), so it gets the same treatment (verified by reading, not probed); the comments/compare/preview surfaces are inferred to match if they use the same renderer. The `transform` is inert while the link is inline, but the stroke is not, and any future `display: inline-block` link would also scale.
- Why it matters: PLAN.md Non-goals: "any change to document typography"; AGENTS.md: the document typeface is independent of the interface. This is interface styling leaking into the manuscript.
- Fix: add `.ProseMirror a`, `.writing-surface a`, `.manuscript-read a`, `.preview-content a` (and the comments/compare bodies if they render links) to the one `:not(:is(...))` exclusion list, in both the transform rule and the hover rule. Fail-first: a Playwright case that sets a link in the editor, hovers its first client rect and asserts `webkitTextStrokeWidth === "0px"` and `transitionProperty` not containing `transform`; it fails on the current tree. Also add `a` inside those containers to `tests/hover-emphasis.spec.ts`'s crawl exclusions, or the crawl will then complain that a "text control" lacks emphasis.

### 2. MAJOR -- focus mode in split view: the shared bar collapses, both panes jump 40 px, and the revealed bar covers the pane headers
- Where: `src/editor/toolbar-motion.css:28-48` (`.writer > .format-bar[data-focus-hidden]`), `src/Writer.tsx:1801-1804` (`data-focus-hidden` set whenever `focusMode && showToolbar`, including when the bar is portalled), `src/Writer.tsx:1833` (`data-focus-toolbar`, the reserved space, only when `toolbarTarget === undefined`), `src/App.tsx:1818-1819` (`showToolbar={side === focusedPane}`, `toolbarTarget = splitToolbar`).
- The portal host `.split-toolbar` carries `className="writer split-toolbar"`, so the `.writer > .format-bar[data-focus-hidden]` rule matches the portalled bar too. The bar goes `position: absolute`, the host's height drops from 40 px to 0, and no space is reserved because `data-focus-toolbar` is never set in split view.
- Scenario (reproduced on the current build): two sections, open one beside the other, click the left editor, Cmd+Shift+F. Measured: `.split-toolbar` height 40 -> 0; the left pane's `.ProseMirror` top 180 -> 140 (both panes' text jumps up 40 px); after moving the pointer to the top, the bar is revealed at y 74-114, exactly over the pane headers (74-106), so "Opening" / "Second" and the Close right pane button are hidden behind it. Toggling focus mode off restores 180. (The intermediate opacity readings from the pane were inconsistent, probably a throttled background pane; the finding rests on the heights and tops.)
- This breaks DoD line 25 ("the page does not jump") and the owner's never-move-the-text rule. T190's note says "Split-view shared bar not changed" and the X1/X1b/X1c specs are single-pane only, so no test covers it; the design-system Focus mode section (`docs/design-system.md:229`) describes the behaviour as if it applied everywhere.
- Fix, pick one: (a) do not hide the bar when it is portalled -- fold the condition into the one variable every site already keys off, `const hidesBar = focusMode && showToolbar && toolbarTarget === undefined;` (`src/Writer.tsx:338`), which also silences the pointermove effect and the `onFocus`/`onBlur`/Escape handlers in split view, then say in design-system and limitations that the shared split bar stays visible in focus mode; or (b) make it work in split: set a reserved `min-height: calc(var(--control-height) + 2 * var(--space-1))` on `.split-toolbar` while the bar is hidden and set `data-focus-toolbar` on the pane whose bar is hidden. Fail-first: a Playwright case in `tests/writing-aids.spec.ts` that opens a split, toggles focus mode and asserts both panes' `.ProseMirror` tops are unchanged within 1 px and `.split-pane-header` is not covered when revealed; it fails on the current tree.

### 3. MINOR -- `label:has(input)` scales the whole label, input box included, and has no keyboard path
- Where: `src/styles.css:417` and `:445` (`label:has(input)` in the emphasis selector), `:490` (`label:has(input)` in the left-origin list); example control `src/App.tsx:2233` (`<label className="settings-field">Total word goal <input type="number" ...>`).
- Scenario: hover the "Total word goal" field in Settings: the label and its number input grow 4 percent together (the stroke on the typed value is correctly zeroed by `:488`, the scale is not). A label is never `:focus-visible`, and focusing the input does not emphasise the label, so this hover effect has no keyboard equivalent, against AGENTS.md "Every hover interaction must have keyboard access". The tests disagree with each other: `tests/hover-emphasis.spec.ts` H2 asserts 1.04 on "settings label", while the H3 crawl explicitly exempts `label` from the scale check (`!/label/.test(r.selector)`).
- Fix: restrict to labels that wrap a checkbox or radio (`label:has(> input[type="checkbox"], > input[type="radio"])`), or drop `label:has(input)` from the scale part and keep only the stroke; align the two spec assertions. Owner call on which.

### 4. MINOR -- docs claim a focus-mode behaviour that split view does not have, and "hides the sidebar" is not what the app does in split
- Where: `docs/design-system.md:229` ("Focus mode hides the sidebar (as before) and, from wave 4, also the formatting bar ..."), `AGENTS.md` / `docs/limitations.md` say nothing about split view.
- In the split probe the sidebar stayed visible after Cmd+Shift+F (`.app` had no `focus` class; `.focus .sidebar` at `src/styles.css:1071` therefore did not apply). Whether that is split-only or general was not established (see "Not established"), but the sentence is at least not true in split view. Rewrite once finding 2 is decided.

### 5. MINOR -- press animation of text controls no longer uses `--duration-press`
- Where: `src/styles.css:437-440` sets `transition: transform var(--duration-fast)` with specificity (0,3,3) (the `:not()` list contains `.topbar > div:first-child > button`), which beats `button:active:not(:disabled)`'s `transition: transform var(--duration-press)` at `:260-263`.
- Effect: every text button now presses over 120 ms instead of the press token; icon buttons still use the press token. `docs/design-system.md` States still says "every button scales to 0.99 over --duration-press". `src/designTokens.test.ts` checks only the `:active` rule body, so it cannot see the override. Fix: add `:active` to the emphasis rule's transition (`transition: transform var(--duration-fast) ...; ` plus a `:active { transition-duration: var(--duration-press) }` in the same block), or amend the doc.

### 6. NIT -- `src/hoverEmphasis.test.ts` (c) only matches `scale(`
- `tests/.../hoverEmphasis.test.ts:44`: `/transform\s*:[^;]*scale\(/` lets `scaleX(`, `scaleY(` and `scale3d(` through. `src/components/scrollspy.css:40-45` already sets `transform: scaleX(0.75)` on `.entry-row > button.spy-line:hover` (intended), so the scan is passing by the gap, not by an allowlist. Widen to `/scale[XYZ3d]*\(/` and allowlist `.spy-line`.

### 7. NIT -- the crawl silently skips controls it could not hover
- `tests/hover-emphasis.spec.ts` H3 loop: `if (!r.hover || r.disabled) continue;` -- a control whose `hoverSample` returned null (off-screen, covered, moved) is not counted and not reported. Count them and assert the count against a small cap, or list them in the output.

### 8. NIT -- `scrollToSection` leaves its wheel/touchstart listeners on the Read scroller after a scroll finishes on its own
- `src/App.tsx:1852-1868`: the listeners are removed only through `cancelReadScroll.current()`, which runs on the next line click or on the first wheel/touch. After an uninterrupted 600 ms scroll they stay attached until one of those happens or the Read view unmounts. Harmless (one pair, element-scoped, GC'd with the scroller), but a `finally`-style removal when `easedScrollTo` completes would be cleaner.

### 9. NIT -- page sheets lag the plugin by one render
- `src/Writer.tsx:1866-1874` draws `pages` sheets from React state, which is set from the plugin's `pageCount` on the next render; the spacer for a new page can exist for one frame before its sheet. This is the same lag `--page-count` (`min-height`) always had, and it is at most one frame. Record, do not fix.

### 10. NIT -- `deleteAcrossBreak` does nothing when the paragraph next to the break is the first/last child of a wrapper
- `src/editor/pagination.ts:646-663`: `$head.before()`/`after()` resolve at the paragraph's own depth, so a paragraph that is the first child of a blockquote or list item after a page break finds `nodeBefore === null` and falls back to ProseMirror's default (select the break node). That is the pre-wave behaviour, so safe; mention it in the design-system paragraph as a limit.

### 11. NIT -- design-system / limitations wording
- `docs/limitations.md` "A revealed focus-mode bar covers text that is scrolled under it ... Printing the live editor in focus mode may keep the extra top band": correct, and the only print path that uses the live DOM is the native-smoke-only probe (`src-tauri/src/printing.rs` header), so it is harmless; say so to avoid alarming the owner.
- `docs/design-system.md` Sidebar selection says "a lit header keeps its colour while pressed" -- true (`src/styles.css:2072`). The claim that `.spy-line` "needs .spy-line added to the text-emphasis exclusion list (T183); the overrides below beat that rule if it is not" (`scrollspy.css:6-7`) is stale: it is in the list (`styles.css:435`). Trim the comment.

## Judgement of the coordinator's two test-only timing fixes
- `tests/scrollspy.spec.ts` (d): polling until the line is `visibility: hidden` or `right <= 0` is a correct wait for the sidebar's slide-out, bounded by `expect.poll`'s default timeout; it does not weaken the claim (the lines must end up hidden with the sidebar). Fine.
- `tests/editor-toolbar.spec.ts` dock test: `toBeLessThan(1.001)` within 1000 ms after the pointer leaves is a tolerance for the last transition frame, not a loosened claim; the inline `--dock-scale` is removed on `pointerleave` (`dock.ts:59-64`), so the computed scale returns to exactly 1 once the 120 ms transition ends. Fine.
