### Findings
- High: none. Medium: none.
- Low (left unfixed):
  1. **Grouping reads ambiguously; owner decision.** A folder's own projects come after its subfolders, at the same left edge and with no heading. In the shots, "Alpha draft" (in Essays, after the Drafts subfolder) looks like a Drafts row or a top-level row, and the top-level projects after Fiction look like Fiction's. This is what the plan prescribes ("subfolders first", heading-only indent), not a worker defect. Ask the owner whether folder contents should be indented or the order changed.
  2. **The last row of each container looks taller.** In list view, rows carry only a top rule. The 24 px stack gap under a container's last row therefore reads as part of that row (a 77 px band against 53 px for other rows). A hairline under the last row of each `.folder-projects` list, or the gap placed before headings only, would fix it. This is cosmetic.
  3. **A wrong-shaped library still loads as empty and stays writable.** A library with the wrong `version`, or with `placement`/`order` missing, parses to an empty library. The next folder edit overwrites the file, and the backup is only one write deep. This is half of REVIEW-1 low 4; the other half (one bad folder entry) is fixed.
  4. **`useLibrary` signature deviation.** It is `useLibrary(onError?)` and also returns `ready` (documented in notes/FB4.md). This is compatible, and FB5 should use it.
  5. Deleting a project leaves its placement entry behind (harmless, noted by the worker). The rename input relies on the browser's default input padding.
  6. **Unreproduced keyboard miss.** In one probe run, Shift+F10 on a heading right after `focus()` had scrolled a 10-project page opened no menu. It did not reproduce in a clean run (it opened every time). It may be the menu closing on a trailing scroll. Unverified.
  7. Chromium against the dev server only. Native WebKit and a real `library.json` in the Mac app were not checked.
