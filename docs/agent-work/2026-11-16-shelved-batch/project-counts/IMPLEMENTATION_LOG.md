## T2 -- counts through both storage paths
Save header is built by `headerOf` in `src/save-queue.ts`; used by SaveQueue.enqueue (journal header), SaveQueue.drain (the Change sent to disk) and `storage.createProjectWithAssets`.
Changed:
- `src/save-queue.ts`: new `savedHeaderOf(p)` = `headerOf(p)` + `projectCounts(p)` (spread, so keys overwrite stale ones, never duplicate). `drain` uses it only when `this.saved?.revision !== p.revision`; a revision already on disk is re-sent with the plain header. Journal header unchanged (no counts).
- `src/storage.ts`: browser `list` adds `...projectCounts(project)`; `createProjectWithAssets` uses `savedHeaderOf`.
- `src-tauri/src/store.rs`: `Summary` gains `word_count`/`section_count: Option<u64>` (skip_serializing_if none); list copies them from `h.extra`; new test `list_copies_word_and_section_counts_from_the_header`.
- Tests: `src/storage.test.ts` (browser list test; native create-project test's pinned header now includes the two keys), `src/save-queue.test.ts` (stamp + overwrite; unchanged revision gets no stamp).
Checked before editing: Rust same-revision retry compares the stored header JSON to the new one and returns "conflict" if they differ; browser save does the same via JSON.stringify. So stamping a revision that is already on disk (e.g. a leftover-journal re-enqueue of an upgraded legacy project) would have turned a harmless no-op into a conflict error. Hence the conditional stamp. Counts are derived from the project at that revision, so a retry of the same revision stamps identical values. validateProject (TS) and validate_header (Rust) ignore unknown keys; Rust Header/Project/Entry carry `extra` flatten; no deny_unknown_fields in store.rs. Incremental-save entry diffing is by entry identity and does not look at the header. Snapshots/history/export copy the header JSON as is (additive keys).

## Amendment: counts computed at list time (coordinator design change)
Why: header stamping made restore/re-save tests fail (stored header differs from the plain re-sent header -> "Conflicting revision"). All stamping reverted.
Reverted: `src/save-queue.ts` (savedHeaderOf, onDisk logic, projectCounts import) and `src/save-queue.test.ts` (two stamping tests): `git diff` on both is empty. `src/storage.ts` createProjectWithAssets back to `headerOf`; pinned header in the native create-project test back to its original. Kept: browser `list` counts, `src/projectCounts.ts`, `Summary` type, all of T3.
Rust (`src-tauri/src/store.rs`): `list` now opens one read transaction per project (same pattern as `read`), reads the header, then `manuscript_counts` runs `SELECT id,data FROM entries WHERE kind='section'`, keeps only ids in the header's `entry_ids`, parses each row's JSON and counts words in its `text` with `js_word_count` (mirrors `words()`: runs of JavaScript whitespace incl. NBSP, U+3000, U+FEFF separate words; empty/whitespace-only -> 0). Entries always live in `entries.data` (the `blob` column is only a history pointer), and commit deletes entries not in the header, so no orphan handling needed beyond the id filter. Any read/parse failure -> counts None; the project is still listed, never moved to `damaged`.
Tests: replaced the Rust header test with `list_counts_words_and_sections_from_the_manuscript_entries` (two sections + a fragment, expects 7 words / 2 sections, including a NBSP/ideographic-space sample) and `list_counts_zero_for_a_project_with_no_sections`; both failed first (left (None, None), right (Some(..)) before the implementation) and pass.
